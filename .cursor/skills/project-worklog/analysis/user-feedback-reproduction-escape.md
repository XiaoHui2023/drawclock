# 用户反馈复现与声明逃逸分析

- status: active
- created: 2026-09-03 13:32 +08:00
- updated: 2026-09-03 16:24 +08:00
- scene: 人工故障冒充复现与声明逃逸根因

## 问题

上一轮把部分自然样本、人工改坏路线的 Oracle 自测、修复后绿灯和全量回归混为“六项都已复现并
解决”。实际缺少逐条旧版本自然红灯，导致 `reproduction_escape` 与 `claim_escape`。

## 根因

1. 项目没有独立的用户反馈问题账本，复合描述被压成一个宽泛目标。
2. 测试合同只有 success/fault，没有独立 `user_reproduction` 证据类别。
3. 变异测试能证明统计器识别形状，却被错误提升为真实输入能产生该形状。
4. 提交/发布门只消费回归结果，没有检查“每条反馈是否先在冻结旧版本经公开入口失败”。
5. 完成声明没有绑定精确 issue 集合，因此局部通过被扩大为全部完成。
6. `.github/workflows/release.yml` 的 build 没有反馈复现前驱；publish 使用 `always()`，扩大了依赖失败时继续求值的旁路面。
7. 项目交付门仅依据 `src/**` 是否变化选择 solve/structure；门禁基础设施提交因此只跑 structure，无法代表可发布。

## 采用方法

- 状态机：`reported -> reproduction_in_progress -> reproduced -> fix_in_progress -> fixed_verified -> closed`。
- 自然复现：冻结 Git revision，以公开 CLI 对有效 JSON 运行两次，原始 SVG 交给只读独立 Oracle；
  runner 绑定命令、输入、产物、baseline tree 和 Oracle 哈希。
- Oracle 自测：人工变异单独记为 `oracle_self_test`，永远不能提升问题状态。
- 产品冻结：自然复现门未绿时，只允许问题账本、有效输入、runner、只读 Oracle 和门禁路径变化。
- 声明约束：全部布局问题关闭前，本轮只能声明复现流程/门禁的已验证范围。
- 发布闭包：本地 pack 先跑自包含 release 门；CI build 显式 `needs` feedback gate，publish 同时依赖 gate 与 build，禁止 `always()`。
- 语义触发：用户表达“仍然、错误、没复现、质量不过关”等负反馈时，托管 hook 先要求写入问题账本；产品路径在登记前不可修改。

## 多对多复现模型

- 问题 ID 与直接 Oracle 保持一对一可追踪，但测试载体不是一对一：一个正常输入可以触发多条问题，一条问题也可以由多个简单或复杂输入触发。
- 覆盖闭包按二部关系 `case -> observed issue ids` 计算；只有所有问题至少有两次冻结基线自然命中，聚合覆盖率才是 100%。测试文件名、设计意图或人工变异不产生覆盖边。
- 统计器独立读取 JSON 与最终 SVG，先证明节点/边数量和端点绑定，再统计规范化折点、异网内部交叉、异网重叠、长度、同源网络环和反事实支配。Oracle 自测用人工几何，用户问题复现只接受公开 CLI 原始产物。
- 首批 36 个组合语料在 `6c9f9f4` 命中 4/6；新增 12 个中间列组合仍未命中剩余两项。未命中意味着继续扩展特征空间或修复历史运行环境，不得据“结构看起来相似”升级状态。
- 历史入口必须按 revision 解析：`3378c1b` 是无子命令 draw-only，`06c4c6c` 使用 `draw` 且依赖 `config-library==0.18.1`。入口/依赖失败属于环境证据，不属于产品症状。
- 当前产品 owner 继续冻结；下一阶段输入是新增正常 JSON，输出是按问题聚合的直接几何证据矩阵。

## 复现规律与版本边界

| 问题 | 自然触发结构 | 直接观测 | 规律/边界 |
| --- | --- | --- | --- |
| ROOT-001 | `source/from/gate` 均为零入度且有输出 | 三种 kind 都进入根集合，节点/边完整绑定 | 根语义只能来自拓扑；它是通用性覆盖，不把 kind 本身当错误 |
| ROUTE-002 | 公共根跨多行复用、三输入固定端口、稀疏根交错 | `public_gate` 的同网线段并集含环 | split–rejoin 是同一网络的分裂—重合—再分裂，需图拓扑判定而非交叉数 |
| ROOT-003 | 公共根纵向干线与消费者附近的单用根横线竞争 | current example 25 稳定 4 个逐边归因交叉 | 根纵序和可行列必须共同优化，局部摆放会把横线穿过公共干线 |
| ROOT-004 | 单用根固定过早且目标端口前存在连续可行位置 | 两根均 2→0 交叉，103.66/109.66→24px | “应在中间”不是固定列；完整器件平移的严格支配才成立 |
| BEND-005 | 公共根、交错多输入端口与跨层排序耦合 | 6c9 pad case 稳定出现 3 条可由 H-V-H 严格支配的边 | 折点异常需同时证明障碍、交叉、重叠和长度不退化，面积不参与补偿 |
| PORT-006 | 两条独占输入支路链深不同，目标端口顺序固定 | 06c example 20 的两支路纵序反转并产生 1 个内部交叉 | 简单断开的同深 mux 未命中；独占祖先、非对称链深与端口约束共同触发 |

搜索阶段的反例同样保留：36 个首轮组合只命中 4/6；新增 12 个中间列组合没有命中 ROOT-004；
12 个简单固定端口 pair 在 06c 全部零交叉，没有命中 PORT-006。它们排除了“只要有低复用根”或
“只要有两个固定端口”就必然失败的宽泛假设，并促使 Oracle 从首列阈值升级为连续位置反事实、
从根直连升级为唯一根祖先支路纵序。

121 节点综合 example 把上述拓扑特征放在同一正常 JSON 中。current 直接命中除 PORT-006 外五项；
冻结 06c 直接命中包含 PORT-006 的五项。历史实现不同导致单次运行不要求承载所有缺陷，但同一输入
跨两个冻结实现的直接观测并集覆盖六项，说明综合载体可复用而判据/版本合同仍必须逐项保存。
